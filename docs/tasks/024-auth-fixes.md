## 1. 🔴 Водителя выкидывает из приложения, если нет интернета
`packages/lubao_core/lib/src/api/api_client.dart → _doRefresh()`: при **любой** ошибке `/auth/refresh` (включая отсутствие сети, таймаут, 5xx) токены удаляются и срабатывает `onSessionExpired` → разлогин. Водитель на границе без связи откроет приложение — и окажется на экране входа, а SMS без сети не придёт. Нарушает решение «водитель на границе может долго быть без связи — не выкидывать его».

Исправить:
- удалять токены и разлогинивать **только** если сервер ответил 401/403 на `/auth/refresh`;
- при сетевой ошибке / таймауте / 5xx — токены сохранить, вернуть ошибку запроса, показать «Нет связи» и повторить refresh при следующем запросе;
- тест: refresh падает с `DioExceptionType.connectionError` → токены на месте, `onSessionExpired` не сработал.

## 2. 🟠 Ограничение 5 попыток ввода кода обходится параллельными запросами
`sms.service.ts` и `email.service.ts → verifyCode()`: счётчик попыток читается (`get`), сравнивается и записывается (`set`) отдельными командами. Если отправить, например, 200 проверок одновременно, все прочитают `attempts = 0` — получится 200 попыток на один 4-значный код.

Исправить:
- атомарно: сначала `INCR attemptsKey` (+ `EXPIRE` при первом), и только если результат ≤ 5 — сравнивать код (или Lua-скрипт get-compare-incr);
- дополнительно лимит на проверку кода с одного IP (например, 30 в час);
- тест: 20 параллельных неверных проверок → не больше 5 сравнений, дальше «запросите новый код».

## 4. 🟡 Две вкладки веб-кабинета разлогинивают логиста
Логист открыл кабинет в двух вкладках. Access-токен истёк — обе вкладки одновременно шлют `/auth/refresh` с одним и тем же refresh-токеном. Первая получает новую пару, вторая попадает в «reuse detected» → **вся сессия отзывается**, логиста выкидывает в обеих вкладках. То же при плохой сети, когда ответ refresh потерялся и клиент повторил запрос.

Исправить:
- grace-период ~30 секунд: если пришёл `previousTokenHash` и с ротации прошло ≤ 30 с — не отзывать сессию, а вернуть актуальную пару (хранить новый access/refresh на короткое время в Redis по `previousTokenHash`) ; после 30 с — как сейчас, отзыв;
- обновление при ротации — условное (`updateMany where { id, refreshTokenHash: hash }`, проверить `count === 1`), чтобы две параллельные ротации не прошли обе;
- тест: два параллельных refresh одним токеном → оба получают валидную пару, сессия жива.
