## Зачем
1. Заблокированный водитель/компания сейчас просто регистрируется заново с другим телефоном. Блокировать надо **идентификатор** (ИИН, номер прав, VIN, госномер, БИН / 统一社会信用代码), а не аккаунт.
2. Админ тратит время, перепечатывая данные с фото и сверяя глазами. Распознавание заполняет поля и само находит дубли.
3. Водители меняют тягачи и особенно прицепы — одна машина в профиле не отражает реальность.

## Этап A. Гараж: тягачи и прицепы (данные)
1. `Vehicle.kind` — enum `TRACTOR` (тягач) | `TRAILER` (прицеп/полуприцеп) | `RIGID` (одиночка: кузов на шасси). Поля: `plateNumber`, `vin`, `brand`; кузов/тоннаж/длина — у `TRAILER` и `RIGID`. `isOwner` (собственник или работает на чужой машине), `isArchived`.
2. **Миграция существующих данных** (правило CLAUDE.md, на базе с демо-данными): каждая текущая `Vehicle` → `TRACTOR` (госномер, марка) + `TRAILER` (кузов, тоннаж, длина); существующие `VEHICLE_PASSPORT` → к тягачу, `TRAILER_PASSPORT` → к прицепу.
3. `VerificationDocument.vehicleId` (nullable) — техпаспорт принадлежит конкретной машине. Статус проверки машины = статус её техпаспорта.
4. **Проверка разделяется:** водитель «Проверен» = селфи + права одобрены (человек). Машина «проверена» = её техпаспорт одобрен. **Подтвердить сделку** можно, если проверены водитель **и** машины выбранной на рейс связки. `REQUIRED_DRIVER_DOC_TYPES` → только `SELFIE`, `DRIVER_LICENSE`; правило для сделки — в `deals.service`.
5. `Arrival.tractorId`, `Arrival.trailerId` (nullable; для `RIGID` — только `tractorId` = сама машина). По умолчанию — связка из прошлого анонса.
6. Логист в «Кто будет» и в отклике видит кузов/тоннаж **связки этой поездки**; лента водителя (016) подбирает грузы по ней.

## Этап B. Гараж: приложение водителя (макет 26)
7. Профиль → «Мой гараж»: разделы «Тягачи» и «Прицепы», статус каждой машины, «+ Добавить машину».
8. Добавление: тип → **фото техпаспорта** → поля (госномер, VIN, марка; для прицепа — кузов, тоннаж, длина) **предзаполнены распознаванием** (этап D), водитель проверяет и отправляет → машина «на проверке». Без распознавания — ручной ввод, ничего не блокируется.
9. В анонсе «Буду на точке» — шаг «На чём еду»: тягач + прицеп (чипы из гаража), по умолчанию прошлая связка. Непроверенная машина — с пометкой «на проверке».
10. Убрать машину — в архив (история сделок сохраняется), не удалять.

12. Нормализация перед хешем: верхний регистр, без пробелов/дефисов; телефон — E.164; госномер — латиница (кириллические А/В/Е/К/М/Н/О/Р/С/Т/Х → латинские двойники).
13. Таблица `blocked_identifiers`: `type`, `valueHash`, `valueMasked`, `reason`, `blockedByUserId`, `createdAt`, `liftedAt?`.
14. При блокировке водителя/компании (028) — галочки «Заблокировать также по: ИИН ✓, номер прав ✓, телефон ✓, VIN/госномера машин …» (по умолчанию все подтверждённые идентификаторы). Разблокировка снимает и их (с причиной).
15. **Проверки совпадений** — при регистрации (телефон), при распознавании, при ручном вводе админом:
    - совпадение с `blocked_identifiers` → документ/аккаунт помечается ⛔, проверка не может быть подтверждена без явного решения админа (с причиной), в «Требует внимания» — строка «Совпадения с чёрным списком»;
    - тот же идентификатор у **другого активного** владельца → ⚠ «дубль: у <ссылка на карточку>» (для госномера — нормальная ситуация при смене владельца машины, поэтому только предупреждение).
16. Полный ИИН/номер прав — только по кнопке «Показать» в админке, каждое раскрытие → `audit_log`. В API наружу — только `valueMasked`.

## Этап D. Распознавание (свой сервер, документы никуда не уходят)
17. Сервис `ocr` в `docker-compose.yml`: открытый OCR-движок с поддержкой **кириллицы и китайского** (например, PaddleOCR в контейнере, CPU), HTTP только во внутренней сети docker (не публиковать порт наружу). Никаких облачных API для документов.
18. Поток: загрузка документа → запись сразу → задание в очередь BullMQ (из 011) → `ocr` возвращает строки текста → **разбор правилами** по типу документа → `DocumentRecognition` (`documentId`, `status` PENDING/DONE/FAILED/SKIPPED, `fields` JSON: `{name: {value, confidence, checksumOk, needsReview}}`, `engineVersion`, `durationMs`). Ошибка/выключенный сервис → `SKIPPED`, проверка идёт вручную как сейчас.
19. Правила извлечения (с **контрольными суммами** — главная защита от ошибок OCR):
    - **ИИН / БИН** (12 цифр) — алгоритм контрольного разряда РК (два прохода весов);
    - **统一社会信用代码** (18 символов) — контрольный символ по GB 32100-2015;
    - **VIN** (17 символов, без I/O/Q) — формат; контрольная цифра (позиция 9) — только как подсказка, не как отказ (вне Северной Америки необязательна);
    - **госномер РК** — форматы физлиц/юрлиц и прицепов (`123 ABC 02`, `777 ABP 05`, прицепы `45 ABC 05`), латиница/кириллица;
    - **номер прав, срок действия** — по шаблону документа; **ФИО** — строки латиницей/кириллицей, сравнение с профилем с транслитерацией (переиспользовать `city_search` translit) и допуском на опечатку.
    Поле без прошедшей проверки или с низкой уверенностью → `needsReview` («проверьте»).
20. Типы документов и поля:
    - `DRIVER_LICENSE` → ФИО, ИИН (если есть на документе), номер, срок действия;
    - `IDENTITY` (если водитель загрузил удостоверение) → ФИО, ИИН;
    - `VEHICLE_PASSPORT` / `TRAILER_PASSPORT` → госномер, VIN, марка, (для прицепа — тип кузова, масса: грузоподъёмность = макс. масса − масса без нагрузки — решение 2026-10-04);
    - `COMPANY_REGISTRATION` → название, БИН или 统一社会信用代码.
21. Тестовый набор: 10–15 синтетических изображений документов (сгенерированных, **без реальных данных людей**) в `backend/test/fixtures/ocr/`, проверка, что ключевые поля извлекаются; юнит-тесты контрольных сумм на валидных/невалидных номерах.

## Этап E. Админка (макеты 25, 22)
22. На экране проверки слева от документа — блок **«Распознано»**: поле, значение (клик — правка), отметка ✓ / «проверьте» / ⚠ дубль (со ссылкой) / ⛔ чёрный список, подсказка «контрольная цифра верна». Внизу — итог по чёрному списку.
23. «Подтвердить водителя / компанию / машину» сохраняет **подтверждённые** значения в `identifiers` (правки админа — в `audit_log` как «распознано X → исправлено Y»).
24. В карточках водителя/компании/машины — блок «Идентификаторы» (маскированные) и история блокировок.
25. На мобильной проверке (030) — блок «Распознано» под документом, тот же функционал.

## Этап F. Право и качество
26. Текст согласия (kk/ru/zh/en): документы распознаются **на серверах Lubao в Казахстане**, ИИН хранится в зашифрованном виде и используется для проверки и защиты от повторной регистрации заблокированных пользователей.
27. Ключи `IDENTIFIER_PEPPER`, `IDENTIFIER_KEY` — только в `.env` (в `.env.example` — пустые), без них сервер не стартует в production. В логах — никаких значений идентификаторов.
28. Тесты backend: миграция гаража на демо-данных; проверка сделки по связке; блокировка с идентификаторами → новая регистрация с тем же ИИН помечается ⛔; дубль госномера → ⚠; раскрытие ИИН пишет `audit_log`; OCR выключен → SKIPPED, всё работает.
29. ARB на 4 языках; `flutter analyze` / `flutter test` чисто; `docs/testing/smoke-test.md` — разделы «Гараж» и «Распознавание».

## Готово, когда
- Водитель добавляет второй тягач и реф-прицеп, фото техпаспорта предзаполняет госномер и VIN; в анонсе выбирает связку, логист видит «реф 18 т».

- Документы не покидают сервер; полный ИИН виден только по кнопке и с записью в журнал.
