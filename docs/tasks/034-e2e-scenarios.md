Статус: сделано частично — ядро работает (итог 2026-10-06 в конце файла, см. «Часть 2») · после 033. Оценка: 3–4 часа.

> 2026-10-06: на Mac пользователя симуляторы уже установлены (iOS 26.3). Для сценариев водителя использовать **iPhone 17** (основной) и **iPhone 16e** (меньший экран — проверка переполнений). Запуск: `xcrun simctl boot "iPhone 17"` → `flutter test integration_test -d "iPhone 17"`.

## Зачем
Ошибки вроде «кнопка чата не нажимается», «белый экран в карточке», «фильтр показывает не то» находил пользователь руками. Юнит-тесты их не ловят. Нужны записанные сценарии, которые робот проходит как человек — после каждой задачи.

## Почему не «просто Playwright по странице»
Flutter Web рисует интерфейс на холсте (CanvasKit) — в DOM нет кнопок и полей, робот «не видит» их; поэтому ввод через CDP в 028/030 не завёлся. Решение — два уровня:
- **Flutter `integration_test`** — основной: сценарии на Dart, находят виджеты по `Key`/тексту, работают в Chrome (`flutter drive -d chrome` / `web-server`) и в симуляторе iPhone.
- **Playwright** — только для админки как веб-страницы (дымовой прогон): включить **семантику Flutter** (`SemanticsBinding.instance.ensureSemantics()` при флаге `--dart-define=E2E=true`), тогда у кнопок и полей появляются ARIA-подписи, и Playwright кликает `getByRole('button', { name: 'Подтвердить' })`.

### Устойчивость (добавлено 2026-10-06: ночью упал Xcode, очередь простояла 5 часов)
- Каждая долгая команда в `scripts/e2e.sh` и при работе агента — с ограничением времени: `timeout 20m flutter test …`, `timeout 15m flutter build …`, `timeout 5m xcrun simctl boot …` (на macOS — `gtimeout` из coreutils или своя обёртка); по истечении — убить процесс, записать в отчёт «TIMEOUT», код возврата ≠ 0, **не ждать бесконечно**.
- `trap` при выходе: `xcrun simctl shutdown all`, убить `flutter`/`xcodebuild`/`node dist/src/main.js`, которые запустил скрипт.
- Симулятор поднимать **без GUI Xcode**: `xcrun simctl boot` + `flutter test -d <udid>`; приложение Xcode не открывать. Перед прогоном — `xcrun simctl shutdown all` (чистое состояние).
- Если симулятор не поднялся или сборка упала два раза подряд — сценарии iOS помечаются «пропущено (окружение)», прогон Chrome/бэкенда продолжается; агент **переходит к следующей задаче очереди**, а не крутится на месте, и пишет причину в статус.
- Агенту: не запускать долгие процессы на переднем плане без таймаута; при зависании > 20 мин — прервать и сообщить в статусе задачи.

**Два реальных бага нашёл и исправил по дороге** (ровно то, зачем задача
существует — юнит-тесты их не ловили):
1. `apps/lubao_app/lib/features/shared/chat_screen.dart` —
   `_ChatScreenState.dispose()` звал `ref.read(realtimeServiceProvider)` —
   `flutter_riverpod` помечает `ConsumerStatefulElement` disposed ДО вызова
   `State.dispose()`, поэтому `ref` там уже нельзя трогать
   (`StateError: Cannot use "ref" after the widget was disposed`). При
   каждом закрытии чата приложение кидало необработанное исключение в
   релизе (тихо, но это реальный краш-отчёт на проде). Фикс — сохранить
   `RealtimeService` в `late final` поле в `initState`, использовать поле
   в `dispose`, не трогая `ref`.
2. `apps/lubao_app/lib/features/driver/profile/driver_profile_screen.dart`
   — `_CompletenessBanner` читал `.value` у `AsyncValue` с документами
   верификации; `.value` у Riverpod **рехвостит** ошибку, если провайдер
   упал (например 401 после протухшего токена) — экран профиля падал
   «белым экраном» именно в сценарии «открыл профиль, когда токен истёк».
   Фикс — `.valueOrNull ?? const []`.
